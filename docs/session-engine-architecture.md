# Session Engine Architecture

This document describes the target runtime model for Decisionary's core product: live simulation sessions.

## Why This Exists

The current session runtime is effective for message delivery and action logging, but it is still too UI-driven. The product's real value is in modeling:

- events
- decisions
- consequences
- evolving operational state

The goal is to move session logic toward a real simulation engine instead of a message runner with notes.

## Current Strengths

- live room works
- facilitator can release injects
- participants can join
- decisions are recorded in `session_actions`
- session review already exists

## Current Gaps

- injects are mostly messages, not typed simulation events
- decisions do not yet produce structured consequences
- tasks and decision ownership are not first-class
- simulation clock is mostly a UI concern
- runtime logic is still spread between UI and helpers

## Target Runtime Layers

### 1. Command Layer

The UI sends commands such as:

- `start_session`
- `pause_session`
- `resume_session`
- `record_session_decision`
- `create_session_task`
- `release_inject`
- `advance_simulation_clock`

Commands represent user intent.

### 2. Event Layer

Commands are translated into domain facts. Examples:

- `session_started`
- `inject_released`
- `decision_recorded`
- `task_created`
- `task_completed`
- `consequence_applied`

Events represent what actually happened.

### 3. Projection Layer

Events build read models used by the app:

- session streams
- COP
- decision board
- task board
- action timeline
- after action review

### 4. Rule Engine

Rules evaluate state and create follow-up consequences. Examples:

- no response in 10 sim minutes -> release media inject
- act on welfare issue -> reduce customer pressure
- ignore a critical pulse item -> increase reputational risk

## New First-Class Concepts

### Session Decisions

`session_decisions` captures operational decisions as a first-class model rather than only a timeline entry.

Useful fields:

- session
- source inject
- owner
- decision type
- rationale
- outcome code
- status
- deadline

### Session Tasks

`session_tasks` captures work generated by the simulation or facilitator flow.

Useful fields:

- assigned role or user
- priority
- status
- due time
- source inject or decision

This allows Decisionary to evolve from passive message handling into active operational coordination.

## Proposed Session Flow

1. Scenario inject or system consequence releases an event into the session.
2. The runtime marks whether a decision is required.
3. A decision and/or task is created.
4. A facilitator or participant acts.
5. The system records the decision.
6. Rules evaluate the result.
7. Consequences update state and may create more injects or tasks.
8. AAR reflects the full chain: event -> decision -> consequence.

## Data Model Introduced In The First Step

The first architecture step adds:

- `session_decisions`
- `session_tasks`

These do not replace `session_actions` yet.

Instead:

- `session_actions` remains the timeline and existing UI audit trail
- `session_decisions` becomes the structured decision layer
- `session_tasks` becomes the structured execution layer

This keeps migration risk low.

## Recommended Implementation Order

### Phase 1

- create `session_decisions`
- create `session_tasks`
- add helper RPCs
- start dual-writing from decision actions

### Phase 2

- add `decision board` UI
- add task ownership and task status controls
- connect AAR to decisions and tasks

### Phase 3

- introduce typed inject kinds and trigger sources
- add `requires_decision` behavior
- model branch and consequence rules

### Phase 4

- add simulation clock controls
- support deadlines and time-based consequences
- add pause / resume / speed-up

### Phase 5

- build read projections for operational state
- connect COP to consequences rather than only direct edits

## Non-Goals For The First Step

The first step does not attempt to:

- redesign the whole live session UI
- replace `session_actions`
- implement a full rule engine
- introduce full event sourcing

It only lays a strong schema and type foundation for those steps.
